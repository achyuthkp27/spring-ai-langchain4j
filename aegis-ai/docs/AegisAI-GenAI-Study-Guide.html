1 · LLM Foundations

A Large Language Model (LLM) is a neural network trained to predict the next token given the tokens so far. That single capability — "given this text, what comes next?" — when scaled to billions of parameters and trained on trillions of tokens, produces something that can answer questions, call tools, and write code. Everything in this guide is built on top of that one primitive: next-token prediction.

An LLM is stateless. It has no memory between calls. Each request sends the entire conversation (system instructions + prior turns + the new message) as one block of text called the context. The model reads all of it and produces a continuation. "Memory" in a chatbot is an illusion we create by re-sending prior turns each time — which is exactly what our ChatMemory does (§15).

The three message roles

  • system — the standing instructions ("You are AegisAI, a bank operations copilot…"). Sets behavior and boundaries.
  • user — what the human typed.
  • assistant — what the model said (prior turns are fed back so it "remembers").
The core mental model
An LLM call = [system + history + user message] → tokenize → neural net → probability distribution over next token → sample one → repeat until stop. Understand this loop and everything else (temperature, streaming, context limits, cost) follows.

2 · Tokens & Tokenization

Models don't see words or characters — they see tokens. A token is a chunk of text, typically a sub-word: common words are one token ("bank"), rarer words split into several ("provisional" → prov+ision+al). The mapping from text to tokens is done by a tokenizer using an algorithm like BPE (Byte-Pair Encoding), which greedily merges the most frequent character pairs into a fixed vocabulary (~50k–100k tokens).

Why tokens matter to you as an engineer

  • Cost & limits are measured in tokens, not words. Rough rule: 1 token ≈ 4 characters ≈ 0.75 words in English.
  • The context window is a token budget (e.g., qwen2.5 default 4096 in our config, others 128k+). System prompt + RAG chunks + history + question + the answer must all fit.
  • Latency scales with tokens generated. The model produces one token at a time (autoregressive), so a 500-token answer takes ~5× longer than a 100-token one. This is why we cap output with num-predict: 1024.
application.yml — capping generated tokens
# The model stops after at most 1024 tokens. Prevents runaway generation,
# bounds latency and cost. Too low → truncated answers (we hit this with 128).
options:
  model: qwen2.5:7b
  temperature: 0.2
  num-predict: 1024
Real bug we hit
Early on, structured-output JSON was being cut off mid-object. Cause: the default output cap was 128 tokens, too small for the JSON. Fix: raise num-predict. Lesson: token limits are a real failure mode, not a theoretical one — a truncated answer looks like a "bug" but is really the model hitting its output budget.

We measure tokens on every call for cost/observability — the TokenAuditAdvisor logs prompt, completion, and total tokens:

TokenAuditAdvisor.java — measuring token usage per call
log.info("ai.call model={} tenant={} elapsedMs={} promptTokens={} completionTokens={} totalTokens={}",
    model, tenant, elapsedMs,
    usage.getPromptTokens(), usage.getCompletionTokens(), usage.getTotalTokens());

3 · Embeddings & Vector Space

An embedding is a list of numbers (a vector) that represents the meaning of a piece of text. An embedding model maps text → a fixed-length vector (ours, nomic-embed-text, produces 768 numbers). Texts with similar meaning land close together in this 768-dimensional space; unrelated texts land far apart. This is the mathematical foundation of both RAG and our semantic cache.

Measuring closeness: cosine similarity

To ask "how similar are two vectors," we measure the angle between them, not the straight-line distance. This is cosine similarity = the cosine of the angle between the vectors:

  • 1.0 = same direction = identical meaning.
  • 0.0 = perpendicular = unrelated.
  • Negative = opposite meaning.

We use the angle (direction) rather than magnitude because meaning is about direction — a long document and a short phrase about the same topic point the same way even if their vectors have different lengths. Here's the exact cosine implementation from our semantic cache:

SemanticCache.java — cosine similarity by hand
private static double cosine(float[] a, float[] b){
  double dot=0, na=0, nb=0;
  for(int i=0; i<a.length; i++){
    dot += a[i]*b[i];      // dot product (alignment)
    na  += a[i]*a[i];      // |a|²
    nb  += b[i]*b[i];      // |b|²
  }
  return dot / (Math.sqrt(na)*Math.sqrt(nb));  // dot / (|a||b|) = cos θ
}

Distance metrics you'll meet

MetricWhat it measuresWhen used
Cosine similarityAngle (direction) between vectorsDefault for text embeddings (ours). Robust to length.
Dot productAlignment × magnitudeWhen vectors are normalized, equals cosine. Faster.
Euclidean (L2)Straight-line distanceSome models; sensitive to magnitude.

Our pgvector index is configured for cosine: distance-type: cosine_distance.

The most valuable embedding insight from this project
Retrieval embeddings ≠ similarity embeddings. They are trained for different jobs:
  • Asymmetric / retrieval (nomic-embed-text): "does this document answer this query?" — query and document are different shapes of text.
  • Symmetric / similarity (all-minilm): "are these two questions the same?" — both sides are the same shape.
Using a retrieval model for question↔question matching (our first cache) gave a tiny separation margin (~0.09 between paraphrases and different questions) → "what is a dispute?" wrongly matched the deadline answer. Switching the cache to a symmetric model (all-minilm) widened the margin to ~0.27 and fixed it. Pick the embedding for the job, not just "an embedding model."

4 · Temperature, Sampling & Randomness

Why does the same question give different answers each time? Because the model doesn't output a single "the next token." It outputs a probability distribution over all ~50k tokens, then samples from it. The knobs that control that sampling are the source of the "randomness" you see.

How the next token is actually chosen

  1. The network outputs a raw score (logit) for every token in the vocabulary.
  2. Temperature scales those logits, then softmax turns them into probabilities that sum to 1.
  3. Optional filters (top-k, top-p) trim the candidate set.
  4. One token is sampled from the remaining distribution. Repeat for the next token.

The knobs, precisely

KnobWhat it doesEffect
temperatureDivides logits before softmax. →0 sharpens (greedy), ↑ flattens.Low = consistent/factual. High = varied/creative. We use 0.2 for banking (want consistency).
top-kKeep only the k highest-probability tokens, sample among them.Hard cap on candidates. k=1 = greedy/deterministic.
top-p (nucleus)Keep the smallest set of tokens whose probabilities sum to p (e.g., 0.9).Adaptive: few candidates when confident, more when uncertain.
repetition/frequency penaltyLowers probability of already-used tokens.Reduces loops and repeated phrases.
seedFixes the random number generator.Same seed + same input + temp>0 → reproducible sampling.
Why we chose temperature 0.2
A banking copilot must be consistent and factual, not creative. Low temperature keeps the model on the highest-probability (most grounded) tokens, reducing the chance it "wanders" off the retrieved policy text. It does not make the model "correct" — that's what RAG grounding and guardrails are for — it just makes it steadier. You cannot reach 0 with most APIs (fully greedy), and you wouldn't want to: a hair of randomness helps it recover from awkward phrasings.
Temperature is NOT a correctness knob
Lowering temperature reduces variance, not hallucination. A confidently wrong model at temp 0 is still confidently wrong. Correctness comes from grounding (RAG), enforcement (guardrails/tools), and evals — never from the temperature dial alone. This is the single most common misconception.

5 · RAG — Retrieval-Augmented Generation

An LLM only knows what was in its training data (frozen at a cutoff) and what you put in the prompt. It does not know your bank's policies. RAG solves this: before answering, we retrieve the most relevant snippets from your documents and augment the prompt with them, so the model answers from your data with citations — instead of from its memory (which would hallucinate).

RAG has two phases: ingestion (offline, build the searchable index) and retrieval (per query, find and inject the right chunks).

Ingestion, step by step (what our IngestionService does)

  1. Load the tenant's Markdown policy docs.
  2. Chunk / split: break long docs into passages small enough to embed and to fit the context window. We use a TokenTextSplitter. Chunking is an art: too big = imprecise retrieval (irrelevant text dilutes the match); too small = lost context (an answer spans two chunks). Overlap between chunks preserves continuity.
  3. Stamp metadata on every chunk — critically tenantId, plus docType, source. This metadata is the load-bearing security control: retrieval filters on it so one tenant can never see another's docs.
  4. Embed each chunk → a 768-dim vector.
  5. Store vector + text + metadata in pgvector.
IngestionService.java — chunk, stamp tenant, store
List<Document> docs = new MarkdownDocumentReader(resource, config).get();
List<Document> split = splitter.apply(docs);          // chunk
for (Document d : split) {
    d.getMetadata().putIfAbsent("tenantId", tenantId);   // security stamp
    d.getMetadata().putIfAbsent("docType", docType);
}
vectorStore.add(split);   // embeds + persists to pgvector
Idempotent ingestion & cache invalidation
Re-running ingestion clears prior chunks first (so duplicates don't skew ranking) and flushes the semantic cache (so no stale answer survives a policy update). Duplicate chunks were a real bug — they doubled a document's "weight" in retrieval and skewed which chunk won.

6 · ANN, HNSW & Vector Search

Retrieval's core question: given the query vector, find the nearest chunk vectors out of potentially millions. The exact answer requires comparing against every vector — brute-force k-NN — which is O(N) per query and too slow at scale. So we use ANN (Approximate Nearest Neighbor) search: trade a tiny bit of accuracy for massive speed (milliseconds instead of seconds).

HNSW — Hierarchical Navigable Small World graphs

The most popular ANN index (and what pgvector uses). Think of it as a multi-layer graph, like a skip-list for vectors:

  • Each vector is a node connected to its nearest neighbors.
  • There are layers: the top layer is sparse (few nodes, long-range links); lower layers get denser.
  • Search starts at the top, greedily hops toward the query through long-range links to land in roughly the right neighborhood, then descends into denser layers to refine — arriving near the true nearest neighbors after visiting only a handful of nodes instead of all N.

The tuning knobs (recall vs speed)

ParameterMeaningTrade-off
MMax neighbor links per node.Higher = better recall, more memory & slower build.
ef_constructionCandidate list size while building the index.Higher = better graph quality, slower ingestion.
ef_searchCandidate list size at query time.Higher = better recall, slower query. The main runtime dial.
Our config & the honest scale caveat
We set index-type: hnsw, distance-type: cosine_distance. But our corpus is 10 chunks — at that size HNSW is configured but functionally irrelevant (brute-forcing 10 vectors is instant). HNSW earns its keep at ~100k+ vectors. Knowing when a technique matters is as important as knowing how it works.

7 · Hybrid Search — BM25 & RRF

Dense vector search is great at meaning ("minimum balance" ≈ "least I must keep") but weak at exact tokens — codes and identifiers like "IFSC code" or "Form 15G" carry little semantic signal even though they're the literal answer. The fix: run a second, lexical search in parallel and merge the results. This is hybrid search.

BM25 — the lexical half

BM25 is a classic keyword-ranking function (the algorithm behind search engines before embeddings). It scores a document by term frequency (how often the query words appear) weighted by inverse document frequency (rare words count more) with saturation (the 10th occurrence of a word adds less than the 1st) and length normalization. It's sparse — it matches literal tokens — which is exactly where dense search is blind.

Dense (vector)Sparse (BM25)
MatchesMeaning / paraphraseExact words / codes
"least balance to keep"✅ finds "minimum balance"❌ different words
"Form 15G"❌ weak signal✅ exact match

RRF — Reciprocal Rank Fusion (merging the two lists)

Dense and BM25 return two separately ranked lists with scores on different scales. RRF merges them without needing comparable scores: each document gets a score of Σ 1/(k + rank) across the lists (k≈60). A doc ranked high in either list floats up; a doc ranked well in both wins. Simple, scale-free, effective.

Status in AegisAI: NOT implemented (deliberately)
We do pure dense search — no BM25, no RRF. At 10 chunks there's nothing to disambiguate, so hybrid search would add latency for zero accuracy gain (our eval is already 100%). It becomes required when the corpus grows past a few thousand chunks or users query exact tokens. Rule: let the eval tell you — add retrieval complexity when a measured accuracy number regresses, not speculatively.

8 · Re-ranking & Cross-Encoders

First-pass search (ANN + BM25) is tuned for speed across millions of chunks, so it's deliberately approximate — it returns maybe the top 50 candidates, not the perfect top 3. A re-ranker then re-scores those 50 much more precisely and returns a trustworthy top 3–5.

Bi-encoder vs cross-encoder — the key distinction

Bi-encoder (what ANN uses)
Encodes the query and each document separately into vectors, then compares (cosine). Because document vectors are pre-computed once at ingestion, search over millions is fast. But the query and document never "see" each other during encoding → less precise.
Cross-encoder (the re-ranker)
Feeds the query and one candidate together through the model in a single pass, so it can attend to their interaction → much more accurate relevance score. But it can't be pre-computed (it needs the query), so it's too slow to run on millions — only on the ~50 shortlisted candidates.

Latency budget: dense ~10–50ms, sparse runs in parallel (≈free on top), cross-encoder ~50–150ms for 50 candidates — the expensive part, because it can't be pre-computed. Status in AegisAI: not implemented (same reasoning as hybrid — corpus too small to benefit).

9 · Agents & Tool Calling

RAG answers questions from documents. But a copilot must also do things: look up a balance, list transactions, open a dispute. That's tool calling (a.k.a. function calling). You describe your functions to the model as schemas; the model, mid-generation, can emit a structured "call this function with these arguments"; your code runs it and feeds the result back; the model continues with the real data.

The security thesis: the model requests, code enforces
The model can request anything — but the tool decides. In AegisAI, every tool: (1) reads the caller's identity from ToolContext (the model never sees or sets it), (2) checks permission inside the tool, (3) enforces tenant isolation. "Excessive agency" (OWASP LLM06) is structurally impossible: the model can ask to move money, but the tool only ever creates a human-approval request. Authority lives in code, never in the prompt.
BankingTools.java — identity & authz enforced inside the tool
@Tool(description="Look up an account's current balance by account id")
public String lookupBalance(@ToolParam String accountId, ToolContext ctx){
  Principal p = principal(ctx);           // identity from context, NOT from the model
  require(p, "account:read");          // authz check in code
  var acct = banking.getAccount(accountId);
  if(!acct.tenantId().equals(p.tenantId()))
      throw new AccessDeniedException("Cross-tenant access denied");  // tenant isolation
  return "Account "+accountId+" balance: $"+acct.balance();
}

Human-in-the-loop (HITL): for money movement we never execute — issueProvisionalCredit creates a PENDING_HUMAN_APPROVAL request. The agent proposes; a human disposes.

10 · Semantic Caching

LLM calls cost seconds and money. But users ask the same question in different words. A semantic cache serves a previously-computed answer when a new question is semantically equivalent to a past one — turning a 3-second LLM call into a ~15ms lookup. It's a cache keyed by meaning, not exact string.

The hard-won lessons baked into our cache

ProblemFix in code
Retrieval embedding gave a thin margin (§3) → wrong answersDedicated symmetric model (all-minilm); threshold 0.62 sits in the wide gap (paraphrases ≥0.74, different ≤0.47)

A failed "couldn't find…" answer got cached & replayedisSafeToCache() excludes refusals/negatives
Account/balance answers (per-user, change over time) cachedA dynamic flag trips when any account tool runs → never cached
Stale answers after a policy changeCache cleared on every re-ingest; 30-min TTL
Cross-tenant leakageCache is per-tenant; one tenant's answer can never reach another
SemanticCache.java — only cache standalone questions
public boolean isCacheable(String q){
  String norm = q.trim().toLowerCase();
  if(CONTEXT_DEPENDENT.contains(norm)) return false;  // "yes","ok","why",pronouns…
  if(norm.split("\\s+").length < MIN_WORDS) return false; // too short to stand alone
  return QUESTION_WORDS.matcher(norm).find();        // looks like a real question
}

11 · Guardrails & Security

An LLM app has a threat surface no traditional app has. The industry reference is the OWASP Top 10 for LLM Applications. AegisAI maps each risk to a concrete, code-level control — never a prompt plea.

OWASP LLM riskControl in AegisAI
LLM01 Prompt InjectionInjectionScreen flags override/exfiltration attempts before the call
LLM02 Sensitive Info DisclosurePiiRedactor masks PAN/SSN/IBAN/email on input and output
LLM05 Improper Output HandlingLeaked tool-call JSON detected & suppressed before it reaches the user
LLM06 Excessive AgencyAuthz inside tools; money movement → human approval only
LLM08 Scope / domain abuseScopeGate classifier blocks off-domain requests
LLM10 Unbounded ConsumptionRate limiter + budget guard + circuit breaker

The advisor chain — a filter chain for LLM calls

Spring AI advisors wrap every model call like servlet filters wrap HTTP. Ours run in order: audit → guardrails (rate limit → budget → injection screen → PII-in → [model] → output moderation) → memory. Enforcement lives here, in code, so it can't be prompted away.

The scope gate — code enforcement, model judgment

A prompt saying "only answer banking questions" is a request the model can ignore (qwen still wrote Python when told not to). The ScopeGate is enforcement: it runs the model as a cheap classifier (IN_SCOPE / OUT_OF_SCOPE) before the main call and short-circuits off-domain requests in code. Crucially it classifies with the recent conversation, so a follow-up like "the 3rd one" is judged in context — no brittle keyword list. Verdicts for standalone questions are cached (330ms → 6ms on repeat).

The authentication keystone
All of the above rests on identity being real. AegisAI uses JWT: a signed token carrying userId, tenantId, role. A JwtAuthFilter verifies the signature on every request and populates the security context. Tenant isolation, tool authz, and per-tenant budgets are only trustworthy because identity is a verified signed claim, not a spoofable header. Auth is what turns the other controls from theater into guarantees.

12 · Resilience — Circuit Breaker & Timeouts

Ollama serializes generation — one model runs at a time. Under concurrent load, calls queue and slow down. Without protection, a slow model pins request threads until the pool is exhausted and the whole app hangs. Two patterns prevent this, both in LlmGuard (Resilience4j):

  • Time limiter — a hard 30s cap that cancels a hung call so no thread waits forever.
  • Circuit breaker — once ≥50% of the last 20 calls fail or run slow (>25s), it opens and fails new calls instantly with "the assistant is busy," shedding load so the model can recover — then half-opens to test before closing.
What the stress test proved
Ramping 1→100 concurrent users, the circuit opened at ~25 users (the single-Ollama saturation point), shed load, and recovered fully afterward. The app stayed responsive under 100× overload instead of collapsing. Resilience buys graceful degradation, not more capacity — capacity needs horizontal model serving (vLLM / replicas / hosted API).

13 · Streaming

Generating a full answer takes seconds; the user stares at a blank screen. Streaming sends tokens as they're produced (via Server-Sent Events), so the first words appear in ~500ms instead of a multi-second wait. Same total time, far better perceived latency.

The guardrail-safe streaming problem
Output guardrails (PII redaction, tool-leak suppression) need the complete text — but you can't un-send a token. Naively streaming raw tokens would leak a card number before redaction could fire. Our fix: sanitize at safe boundaries — buffer tokens until a sentence/newline, run the guardrails on that complete segment, then flush it. Sentence boundaries never fall inside a PAN/SSN/IBAN/email, so nothing leaks across the boundary. Input guards (rate/budget/injection) run once up front. This is a genuinely subtle production pattern.
A real framework bug we caught
Streaming + tool-calls with Ollama threw NullPointerException: evalDuration is null in Spring AI 1.0.0 — the tool ran but the follow-up stream crashed. Fixed by bumping the BOM to 1.0.9. Lesson: the Java GenAI ecosystem is younger; pin to patched versions and test the streaming+tools path specifically.

14 · Observability & Evals

You can't improve what you don't measure, and LLM output is non-deterministic — so evaluation is the regression net. Two distinct things must be measured, and conflating them is a classic mistake:

Performance (does it stay up?)
Latency percentiles (p50/p95/p99), throughput, error rate, circuit state, token/cost metrics (Micrometer → Prometheus). Answered by the stress test.
Accuracy (is it correct?)
Does the answer contain the right facts? Answered by a golden-fact eval — known questions with expected values (120 days, $5,000…), graded deterministically. A separate concern from performance.
The lesson that cost us the most
"It stayed up under load" and "it gives correct answers" are two different claims. Our stress test measured only the first — it discarded the answer text. When we finally built an accuracy eval, it surfaced a real bug (a varchar(36) chat-memory column overflowing on realistic identifiers) that no performance metric would ever catch. Always eval correctness separately, and wire it into CI so a retrieval or prompt regression fails the build.

16 · Code Walkthrough — the request lifecycle

Here's exactly what happens when a user sends a message to /api/assistant/stream, in order:

  1. JwtAuthFilter verifies the Bearer token's signature → puts the Principal (userId, tenantId, role) in the security context. No token / bad token → 401.
  2. Input guards (streaming bypasses advisors, so the controller enforces them): rate limiter → budget → injection screen. Any trip → instant refusal, no LLM.
  3. Semantic cache lookup (per-tenant). Hit → stream the cached answer as one chunk (~15ms), done.
  4. Scope gate (context-aware classifier). Off-domain → canned redirect, no main call.
  5. PII redaction on the input.
  6. The guarded model stream: llmGuard.guard(assistant.prompt()…stream()) — circuit breaker + timeout wrap the token flux. The model may call tools mid-stream (each enforcing authz + tenant).
  7. Boundary-buffered output sanitization: accumulate tokens; at each sentence/newline, redact PII & drop leaked tool-calls, then flush that segment as an SSE event.
  8. On completion: cache the answer if safe (not dynamic, not a refusal), record token usage against the budget, emit a final meta event (source, elapsedMs).

17 · Frameworks vs Raw Code

A recurring real-world question: LangChain (or Spring AI) vs calling the model SDK directly?

Why raw is faster
The network call is identical either way; frameworks add overhead in two forms: (1) a small per-call tax (prompt templating, callbacks, parsing) of tens of ms; (2) the bigger one — hidden extra LLM calls (agent loops, output-fixing retries). Configure the framework to do the same work (single call, matched params, no agent) and the times converge — the residual tax is negligible against a multi-second LLM call. The features that make a framework convenient (agents, auto-retry) are the same ones that add latency.
The trade, decided honestly
To learn cutting-edge GenAI → Python raw/light. Richest ecosystem; re-rankers & sentence-transformers are one import. For a secure banking copilot on a JVM stack → Spring AI. A banking app is ~80% enterprise plumbing (auth, resilience, observability, ops) — Java's strength — and ~20% "call the LLM." Production shops often do both: Java/Spring for the app + a small Python sidecar for ML-heavy bits (embeddings, re-ranking). Go raw on the hot path when latency is the constraint; keep the framework where developer speed and built-in patterns matter more.

18 · What Still Needs Learning

You now understand the foundation. To reach true production-grade at banking scale, here's the honest roadmap — grouped by why each matters.

Retrieval at scale

  • Hybrid search (BM25 + RRF) — needed once users query exact tokens (codes, form names) or the corpus grows.
  • Cross-encoder re-ranking — the accuracy pass over a shortlist; needed past a few thousand chunks.
  • Advanced chunking — semantic/hierarchical chunking, parent-document retrieval, contextual retrieval.
  • Evaluation frameworks — RAGAS-style metrics (faithfulness, context precision/recall) wired into CI.

Model & generation depth

  • Sampling internals — logits, softmax, top-p/top-k interplay, mirostat, speculative decoding.
  • Fine-tuning vs RAG vs prompting — when each wins; LoRA/QLoRA, instruction tuning.
  • Structured generation — grammar/JSON-schema-constrained decoding for guaranteed-valid output.
  • Multimodality — images/PDFs/audio as inputs (statement scans, cheque images).

Scale & serving

  • Horizontal model serving — vLLM (continuous batching, PagedAttention), multiple replicas, hosted APIs. This is the real fix for the throughput ceiling the stress test exposed.
  • Distributed cache — Redis-backed semantic cache so hits are shared across instances.
  • GPU economics — batching, quantization (GGUF/AWQ), KV-cache, cost-per-1k-tokens modeling.

Security & agents

  • OAuth2 on the MCP endpoint — currently open for the POC.
  • NER-based PII — names/addresses (beyond regex for cards/SSN/IBAN/email).
  • Multi-agent orchestration — planner/executor, evaluator-optimizer loops, MCP client for external tools.
  • Jailbreak & red-teaming — adversarial suites, prompt-injection benchmarks, guardrail models (Llama Guard).
The one principle to carry into all of it
Prompts are requests; code is enforcement; evals are the regression net; the model is the lever, not the rules. Every hard problem in this guide was solved by moving the guarantee out of the prompt and into code, choosing the right model/embedding for the job, and letting a measured number decide when to add complexity. Master that judgment and the specific techniques are just tools.

Cross-encoderScores a query+document pair jointly in one pass; accurate re-ranker, not pre-computable.
EmbeddingA vector representing text meaning; similar meanings → nearby vectors.
HNSWHierarchical Navigable Small World — the popular multi-layer-graph ANN index.
Hybrid searchDense (vector) + sparse (BM25) search combined, usually via RRF.
LogitRaw pre-softmax score the model assigns each vocabulary token.
HITLHuman-in-the-loop — a human approves consequential actions (e.g., money movement).
MCPModel Context Protocol — a standard for exposing tools/resources to LLM clients.
PIIPersonally Identifiable Information (card numbers, SSN, IBAN, email…).
RAGRetrieval-Augmented Generation — inject retrieved documents into the prompt to ground answers.
Re-rankerSecond-stage model that re-scores retrieval candidates for precision.
RRFReciprocal Rank Fusion — merges ranked lists via Σ 1/(k+rank); scale-free.
Semantic cacheCache keyed by meaning (embedding similarity) rather than exact string.
SoftmaxTurns logits into a probability distribution summing to 1.
SSEServer-Sent Events — one-way server→client streaming over HTTP (used for token streaming).
TemperatureSampling knob scaling logits; low = focused/deterministic, high = varied/creative.
TokenSubword unit the model reads/produces; ~4 chars in English.
top-k / top-pSampling filters: keep the k best tokens / the smallest set summing to probability p.
Vector storeDatabase indexing embeddings for similarity search (ours: pgvector).
